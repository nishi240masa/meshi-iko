# レビュー観点（汎用 + セキュリティ）

観点 ID（英字）をレポートの「観点」欄にそのまま使う。ここと `stack-checks.md` にない ID は使わない。

## 汎用観点
- `design-docs`: Step 3 の結果（docs未更新・docs矛盾・docs記載なし・生成コード手編集）。
- `architecture`: 3.1 の方針と揃っているか。レイヤをまたぐ依存（ハンドラから直接DB、UIコンポーネントから直接 fetch）、責務の混在、同じ種類の処理が2通りの書き方で存在しないか。バックエンドは handler → usecase → domain の向きを守り、infrastructure は domain のインタフェースを実装しているか。
- `functionality`: 境界値、nil・空・ゼロ値、エラー経路、並行実行、冪等性。「今日」はサーバが JST で決めているか、締切（18:00）前後や日付をまたぐときの振る舞い。
- `complexity`: 今必要のない汎用化・抽象化・設定項目・拡張ポイントは積極的に指摘する。
- `maintainability`: 命名、重複、肥大化、マジックナンバー、コメントが「なぜ」を説明しているか、デッドコード、既存規約との一貫性。コメントの句読点が「．，」か。
- `tests`: 変更に見合うテストがあるか、壊れたときに本当に失敗するか、異常系と境界値、実装の細部に結合しすぎていないか。
- `error-handling`: 握りつぶし、文脈付きのラップ、利用者向けメッセージへの内部情報の漏れ、エラーレスポンス形式が `openapi.yaml` と一致しているか。
- `observability`: 障害時に原因を追えるログがあるか、ログに秘密情報や個人情報が出ていないか。
- `performance`: N+1、上限のない一覧取得、直列にする必要のないI/O、不要な再レンダリング、バンドルサイズ、Lambda のコールドスタート。
- `security`: 下のセキュリティ節。
- `compatibility`: API・DB・保存データの後方互換。古いAPK、キャッシュされた古いPWA、古いウィジェットがしばらく残ることへの配慮。
- `docs`: README、設計ドキュメント、コメントの更新漏れ（設計判断レベルでないもの）。
- `ux-a11y`: ローディング・エラー・空の状態、ラベル・フォーカス・コントラスト、オフライン時の振る舞い。

## セキュリティ（観点ID: `security`。OWASP API Security Top 10 2023 を軸にする）
- BOLA: IDでデータを取る・更新するとき、所有者をリクエストの値ではなくセッションの userID で照合しているか。
- BFLA: 管理用APIに `X-Admin-Token` の検証が漏れなく掛かっているか（ルートの登録漏れ、ミドルウェアの適用順）。
- 認証とセッション: 暗号論的に安全な乱数、DBにはハッシュで保存、失効（ログアウト）、定数時間比較、トークンをログ・エラー・URLに出さない。
- 過剰なデータ露出・マスアサインメント: レスポンスに不要なフィールドがないか、リクエストをそのままモデルにバインドしていないか。
- インジェクション: GORM の文字列を受け取るメソッド（`Where` の文字列条件、`Order`、`Select`、`Group`、`Having`、`Raw`、`Exec`、`Joins`、`Table`、`gorm.Expr`）にユーザー入力を連結していないか。並び替え列などは許可リストで絞っているか。
- リソース消費: ページングの上限、ボディサイズの上限、タイムアウト。
- 秘密情報: ハードコード、リポジトリへの混入、フロントや Scriptable スクリプトへの埋め込み。
- CORS とセキュリティヘッダ: Lambda 関数URLと Cloudflare Pages の設定が設計どおりか。

報告しないもの:
- `dangerouslySetInnerHTML` などを使わない React の XSS。
- サーバー側で守られているときの、クライアント側の権限チェック漏れ。
- 依存ライブラリが古いこと自体。
- 攻撃経路を説明できない理論上の問題。
- userID だけでログインできること（なりすまし）。DesignDoc §9 で受け入れ済み。ただし、ログイン済みの利用者が他人のデータを操作できる経路（BOLA）は報告する。
